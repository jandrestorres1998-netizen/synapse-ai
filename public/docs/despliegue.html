Despliegue en producción

Recomendaciones para instalar SynapseAI en servidores de empresa: protección con proxy inverso, certificados de seguridad, copias de respaldo del registro de auditoría y rotación ordenada de credenciales.

Última revisión: Septiembre de 2026 · Versión 2.0.0

Arquitectura de producción

Por diseño, el servidor interno de SynapseAI expone tráfico HTTP plano en el puerto 3000 (o el definido en PORT). En un entorno real de empresa, el programa nunca debe exponerse directamente a internet sin un intermediario que gestione los certificados de cifrado y filtre accesos no autorizados.

La topología recomendada sitúa un proxy inverso fiable (como Nginx o Caddy) en la frontera del servidor o de la red interna:

  • Cifrado punto a punto (TLS/HTTPS): Todo el tráfico entre vuestros programas y SynapseAI viaja cifrado mediante certificados SSL/TLS actualizados.
  • Aislamiento de red: SynapseAI escucha únicamente en la interfaz local (HOST=127.0.0.1) o dentro de una red privada virtual de Docker.
  • Terminación de certificados: El proxy inverso asume la carga criptográfica y renueva automáticamente los certificados.

Configuración con Nginx

Si utilizáis un servidor Linux tradicional (Debian, Ubuntu, RHEL) con Nginx instalado, esta es la configuración de bloque de servidor recomendada:

server {
    listen 443 ssl http2;
    server_name ai.vuestra-empresa.local;

    ssl_certificate     /etc/ssl/certs/synapse.crt;
    ssl_certificate_key /etc/ssl/private/synapse.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;

    # Límite de cuerpo para mensajes grandes o documentos adjuntos
    client_max_body_size 10M;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;

        # Cabeceras estándar para propagar IP real y protocolo
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Soporte para respuestas en flujo continuo (streaming de LLM)
        proxy_set_header Connection '';
        proxy_buffering off;
        proxy_cache off;
        chunked_transfer_encoding on;

        # Tiempos de espera generosos para respuestas largas
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }
}
Para tu equipo técnico · Salto de proxies: Cuando colocáis Nginx delante de SynapseAI, debéis configurar TRUST_PROXY_HOPS=1 en vuestro archivo .env. Con este ajuste, el limitador de tasa de SynapseAI utilizará la dirección IP real del cliente reportada en la cabecera X-Forwarded-For en lugar de bloquear la IP local del proxy.

Configuración con Caddy

Caddy es la alternativa más sencilla para servidores modernos, ya que gestiona y renueva automáticamente certificados HTTPS válidos sin necesidad de configurar scripts externos:

ai.vuestra-empresa.local {
    reverse_proxy 127.0.0.1:3000 {
        # Desactivar buffer para respuestas inmediatas de la IA
        flush_interval -1
    }
}

Seguridad del almacén de claves (Vault)

SynapseAI guarda las claves de proveedores de IA (OpenAI, Anthropic, Google) cifradas en disco dentro de su almacén interno. Para garantizar un cifrado de nivel bancario en reposo:

  • Definir siempre SYNAPSE_VAULT_KEY: Si esta variable no está presente, el programa arranca en modo advertencia (machine), derivando una clave provisional de los identificadores del equipo.
  • Generar una clave con entropía alta: Utilizad al menos 32 bytes aleatorios en formato hexadecimal:
# Generar clave segura de 32 bytes en terminal
openssl rand -hex 32
Hasta aquí llega: Si perdéis el valor de SYNAPSE_VAULT_KEY, las claves almacenadas no se podrán descifrar. SynapseAI no guarda copias de rescate de vuestra clave maestra en ningún servidor externo. Tendréis que volver a introducir las claves de los proveedores en el panel.

Copias de seguridad del registro de auditoría

El registro de auditoría es la prueba documental de qué peticiones cruzaron el sistema y qué datos se borraron. Toda la información persistente vive en la carpeta data/:

  • data/audit.jsonl: Registro encadenado de peticiones firmado por SHA-256.
  • data/vault.enc: Almacén de credenciales cifrado.
  • data/budget.json: Contadores de consumo de tokens y presupuesto preventivo.

Para realizar copias de seguridad consistentes sin detener el servicio:

# Copia diaria automatizada mediante cron o tarea programada
tar -czf /backups/synapse-$(date +%Y%m%d).tar.gz -C /ruta/a/synapse data/

Si utilizáis volúmenes en Docker, asegurad el volumen montado (-v ./data:/app/data) incluyendo esa ruta en vuestro plan habitual de copias de seguridad de la infraestructura.

Política de rotación de claves

Para mantener una higiene de seguridad impecable sin provocar caídas en vuestros programas:

  1. Claves de operador (SynapseAI): Generad una clave nueva con el ámbito requerido (inference: o report:) en la pestaña Ajustes del panel. Actualizad vuestras aplicaciones cliente con la nueva clave. Solo cuando hayáis verificado que el tráfico entra correctamente, proceded a revocar la clave antigua.
  2. Claves de proveedores de IA: Actualizad las claves en la consola de OpenAI o Anthropic e introducid la nueva clave en SynapseAI. El cambio se aplica en memoria de forma instantánea sin reiniciar el contenedor.

Comprobación de estado y monitorización

El servicio ofrece una ruta pública y ultraligera para sondas de monitorización (Nagios, Zabbix, Uptime Kuma, AWS Route53 o Kubernetes health probes):

curl -s -i http://127.0.0.1:3000/healthz

Responde con código 200 OK y un documento JSON que certifica que el proceso se encuentra activo y listo para procesar peticiones.
